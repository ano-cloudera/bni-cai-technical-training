# Educational notebook redesign (plan and handoff)

Status: plan only. Nothing in this document is implemented. Branch `feature/single-project-csv-workshop`, baseline
`6529e38`. No push, no CAI deployment, no CAI API call. CAI readiness is not claimed.

## 1. Current-state assessment

The 13 notebooks in `notebooks/templates/` (generated by `scripts/build_notebooks.py` from `config/workshop/labs.yaml`)
execute and pass locally, but they are wrappers. Every notebook has the same shape:

| Cell | Content | Verdict |
|---|---|---|
| markdown | Title, audience, theory paragraph, expected outcome (from the registry) | Educational but one paragraph, identical structure everywhere |
| code 2 | `find_repo_root`, `sys.path`, `LAB_MODE`, `GROUP_ENV_FILE` | Setup boilerplate; keep, but shrink into one imported helper |
| code 3 | `resolve_lab_context(LAB_MODE)` and `describe()` | Wrapper-light and useful (shows GROUP_ID, DATASET_ID, MISSION_ID, workspace); keep |
| code 4 | `get_lab(id)`, `load_script_module(lab.script_path)` | **Wrapper**: dynamic import of the lab script |
| code 6 | `module.main(['--mode', LAB_MODE])`, outcome mapping, assert | **Wrapper**: the whole lesson is one call |
| code 8 | List `output/*.json` | Minor, keep as a "what was saved" step |

Notebooks 01 and 02 add a trainer-role guard cell (good) before the same wrapper. Nothing in notebooks 03-12 shows a
request payload, a SQL statement, a semantic plan, a CrewAI agent or tool, a Qdrant filter, a span, a gateway route or
a guardrail rule. The learning logic lives in `scripts/NN_*.py` (for example `09_phoenix_monitoring.py` is 240 lines,
`07_qdrant_rag.py` 115, `12_end_to_end_portal.py` 109) and in `src/bni_training/`. The scripts and library are sound,
tested and must stay. The notebooks must be rewritten so the important steps are visible cell by cell.

Execution model today: one workspace per **group** (`workshop/runtime/groups/<group_id>/`). A folder is not a Session;
no participant-level folder, identity or mode exists. `config/workshop/topology.single-project.yaml` assumes at most
10 CPU Sessions (one per group). The `participant` dependency profile has CrewAI, OpenAI, httpx and the OpenTelemetry /
OpenInference trace clients but **not** `qdrant-client` or `sentence-transformers` (those are in `rag`).

## 2. Learning objectives

After the hands-on a participant can:

1. Call a shared OpenAI-compatible endpoint with an explicit request payload and read latency, usage and errors.
2. Query a mission's CSV tables with guarded read-only SQL and explain why other tables and columns are refused.
3. Turn a business question into a metric and breakdown through the semantic layer and read the SQL it plans.
4. Build a CrewAI tool bound to their group and an agent that uses it.
5. Index and retrieve group-scoped documents in Qdrant and show the mandatory `group_id` filter.
6. Compose two agents into a workflow and describe what each step contributed.
7. Emit and find their own traces in Phoenix with group, dataset and mission attributes.
8. Route requests through LiteLLM and explain aliases, fallback and keys.
9. Write and test input and output guardrails.
10. Use the shared Workshop Portal and relate what it does to what they built by hand.

## 3. Trainer versus participant responsibility

| Owner | Responsibility |
|---|---|
| Trainer | Notebooks 01 and 02; deploying and validating the **one** shared vLLM Application (one GPU) before hands-on; Qdrant, Phoenix, LiteLLM and the single Portal; workspace generation; roster and mode choice; service checks; resets and archives |
| Participant | Notebooks 00 and 03-12 from a **CPU-only** Session; never downloads the model, never starts vLLM, never creates shared services |

Participant hands-on begins with notebook 03. Notebook 00 is run by everyone first. The model is already serving
before any participant opens notebook 03; notebook 03 only connects to the shared URL. Trainer solutions never show
anomaly answers and no notebook reveals the Group 06 patterns.

## 4. Execution modes

Selected by `PARTICIPANT_MODE` (names only; written to `group.env`, non-secret). The default is `group_driver`.
`individual_learning` is optional only after the trainer validates CAI Session capacity.

| | `individual_learning` (optional after capacity validation) | `group_driver` (default) |
|---|---|---|
| Sessions | up to about 40 CPU Sessions, one per participant | 10 CPU Sessions, one per group |
| Notebook copy | one per participant | one per group |
| Output folder | `groups/<g>/participants/<participant_ref>/output` | `groups/<g>/output` |
| Identity | anonymous `PARTICIPANT_REF=participant_01` through `participant_04`; no CAI identity dependency | the same anonymous labels rotate as drivers |
| Shared | `group_id`, mission, dataset bundle | same |
| Concurrent writes | none inside a participant folder | one writer at a time (the driver); notebooks say so |

Rules for both modes:

- A folder is **not** proof of a Session. The 40-Session quota, per-Session resources (starting point 2 vCPU / 8 GB
  each, 80 vCPU / 320 GB in total plus the shared Applications) and start-up time are `cai-validation-pending`.
  Fall back to `group_driver` when the quota is lower; both modes use the same notebooks and the same group mission.
- Waves (A: groups 01-05, B: 06-10) still only change scheduling.
- Participant identity is for output folders and trace attributes only. It is not an isolation boundary; Qdrant and
  the data tool still isolate by `group_id`. Group separation stays operational, not a security boundary.
- Max 5 active Applications is unchanged: vLLM, Qdrant, Phoenix, LiteLLM, one Portal.

## 5. Shared-service assumptions

One vLLM Application (Qwen3.5-9B, BF16, TP=1, one GPU) is running and healthy before participants start. Notebooks
read `VLLM_BASE_URL`, `LITELLM_BASE_URL`, `QDRANT_URL`, `PHOENIX_COLLECTOR_ENDPOINT`, `PHOENIX_UI_URL`,
`WORKSHOP_PORTAL_URL` and keys from the Session
environment; no host, port, path or token is written in a notebook. Notebooks never start, stop or deploy a service.
`scripts/check_shared_services.py` is the trainer's gate before each phase.

## 6. Code reuse boundaries

Allowed imports (low-level, testable, do not hide the lesson): `bni_training.workshop.lab_context.resolve_lab_context`,
`bni_training.data.{bundles,tool,engine,dictionary,semantic_layer}` classes and their public methods,
`bni_training.llm_client.OpenAICompatibleClient`, `bni_training.mock_llm.MockOpenAIServer` (local mode only),
`bni_training.rag` building blocks (`build_group_filter`, `ensure_collection`, `index_group_documents`,
`search_group`, `HashingEmbedder`), `bni_training.guardrails` validators, `bni_training.observability.safe_trace_attributes`,
`bni_training.crew.RecordingDataTool` and `kickoff_blocking` (Jupyter event-loop workaround only).

Forbidden in a notebook (enforced by tests, section 11): `get_lab`, `load_script_module`, `delegate`, any `.main(`,
`runpy`, `exec`/`eval` of repository code, `inspect.getsource`, reading or printing `scripts/*.py`, `LabReport` /
`run_lab` as the lesson, and one-call helpers that perform a whole workflow (`run_crewai_question`,
`CreditInsightWorkflow.run`, `answer_question`) as the **core** step. Those remain reference solutions: the notebook
builds the same thing in visible cells and may compare its result with the reference at the end.

New reusable code (small, tested, in `src/bni_training/`): a notebook setup helper (repo-root discovery,
`LAB_MODE`, mode, context) to replace the 15-line boilerplate cell; a `participant` identity/paths helper; a status
helper that prints `LAB_STATUS` for the executor. None of them contains lesson logic.

## 7. Exercise design

Every participant notebook ends with one **safe, runnable exercise** that has a working default so automated
execution still passes: a clearly marked cell `# EXERCISE` with a default value the participant changes (a different
metric, a second dimension, a new document, a new guardrail pattern). Rules: read-only; scoped to the group; the
default result is asserted in the next cell with a friendly hint on failure; a trainer-solution cell is collapsed text
in a trainer-only section and never contains anomaly answers or Group 06 findings. Exercises never write outside the
participant (or group) output folder.

## 8. Local mode and CAI mode

| | `--mode local` | `--mode cai` |
|---|---|---|
| LLM | `MockOpenAIServer` started in the notebook process, announced in a cell | real `VLLM_BASE_URL` / `LITELLM_BASE_URL` |
| Qdrant | local mode in memory with `HashingEmbedder` | `QDRANT_URL`, real embedder |
| Phoenix | in-process exporter or temporary local Phoenix | `PHOENIX_COLLECTOR_ENDPOINT` and `PHOENIX_UI_URL` |
| LiteLLM | local stub or SKIPPED | real gateway |
| Portal | in-process `PortalService` with the mock | `WORKSHOP_PORTAL_URL` health plus a saved answer |
| Missing prerequisite | SKIPPED with a reason | **FAIL**, with the variable name; never a silent mock |

A notebook prints one `LAB_STATUS` line (PASS, SKIPPED, FAIL) so `scripts/execute_notebooks.py` keeps working.

## 9. Error handling

Each external call sits in a cell that catches the specific failure and prints a participant-readable cause and next
step (service unreachable, 401/403, timeout, queue busy, refused table or column, unknown group). Pattern: show the raw
error class once, then the plain sentence; never a bare traceback for an expected failure, and never a secret in the
message. In cai mode an expected failure ends the cell with FAIL and a pointer to the trainer; in local mode the same
step is SKIPPED only where the lab contract says so (GPU, NFS, CAI, Impala).

## 10. Notebook-by-notebook design

Common to all: stripped before commit; no hard-coded host, path or token; cells at most about 20 lines, one idea per
cell; markdown sections *Theory*, *Steps*, *Exercise*, *Expected result*; outputs only to the workspace output folder;
a header cell with audience, duration and mode. Durations are planning estimates for the hands-on, not measurements.

### 00 Environment Validation
- Audience: trainer and participant. Duration: 10 min.
- Theory: why validate first; what comes from `group.env` (GROUP_ID, DATASET_ID, MISSION_ID, workspace, mode).
- Direct code cells: print Python version, check variable names (not values), resolve the context and show it, confirm the dataset checksum file and a row count of one table, write a tiny probe file to the output folder.
- Reusable imports: `resolve_lab_context`, setup helper.
- Exercise: select the assigned anonymous `PARTICIPANT_REF` or active driver label and confirm the output folder.
- Expected: PASS; GPU steps SKIPPED (participant Sessions are CPU-only).
- Local: temporary workspace as today. CAI: missing GROUP_ID fails, never guessed.
- Trainer notes: confirm every Session shows the right group before moving on.
- Tests: context cells, no GPU requirement, identity in both modes, hygiene.

## 11. Testing strategy

New gates in `tests/workshop/` (initially with an allow-list of not-yet-migrated notebooks, removed in the last commit):

1. **Anti-wrapper**: no forbidden call or import from section 6 in any participant notebook cell (AST on code cells).
2. **Structure**: required markdown sections, at most about 25 lines per code cell, an `# EXERCISE` cell with a default, a closing `LAB_STATUS`.
3. **Directness**: per-notebook required visible artifacts (for example 06 contains `Agent(`, `Task(`, `Crew(`; 07 contains the printed filter; 09 contains a span with the three attributes; 11 contains the rules).
4. **Execution**: all 13 execute through `scripts/execute_notebooks.py` locally in both modes (`individual_learning`, `group_driver`) from a generated workspace.
5. **Trainer-only**: 01 and 02 stop for non-trainers in cai mode; no vLLM start or model download anywhere (AST).
6. **No leaks**: no `data/csv`, host, token, absolute path or anomaly answer; hygiene and path audit keep passing.
7. **Mode matrix**: identity, output folder and trace attributes per mode; 40 individual participants get 40 separate folders with no overlap; group_driver 10 folders.
8. **No silent mock**: in cai mode every service step fails clearly when its variable is missing.
9. **Reference parity**: the scripts still pass (`tests/integration/test_labs_local.py` unchanged) and a notebook's final answer equals the reference solution on a fixed question.

The existing 697 tests must keep passing at every commit.

## 16. Rollback strategy

Each commit stands alone and is reverted with `git revert` (never a history rewrite). Because scripts, `src/` and the
rc1 notebooks are unchanged, reverting a notebook commit restores the working wrapper notebook for that lab while the
others keep the new design. The allow-list lets a half-migrated state pass. Workspace generation changes are additive
(`group_driver` equals today's layout), so reverting commit 1 loses only the participant folders.
